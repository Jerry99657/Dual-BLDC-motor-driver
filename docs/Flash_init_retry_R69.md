# R69：Flash 启动识别有限重试

2026-10-25，固件 **UI-R69-6STEP**。用户反馈 R68 切换 4015→2804 后出现 `Save NO FLASH`，随后复位又可以保存。

## 已核对的事实

- R68 相比 R67 的生产修改仅为 UI 型号切换顺序、提示和版本号，没有修改 SPI2 初始化、GPIO、分频、ENC2 仲裁、W25Q64 或 AppStorage。
- `Save NO FLASH` 仅由开机 `AppStorage_Init()` 在 ID 识别失败时设置；该初始化在生产代码中只从 main 的启动路径调用。型号切换及后续页擦写不会设置此错误。
- 错误可能在初始化已存在、到换型触发保存时才被看到；未取得当时 ID／HAL／总线寄存器，不能确认这就是此次触发顺序，也不能认定为某个 SPI 模式错误或硬件故障。
- 原来只读取一次 JEDEC ID；一次失败后保存就一直处于未就绪，后续没有再识别。这是可复现的恢复能力缺口。
- About 的 Flash 行只是固定型号文字 `W25Q64`，不是芯片识别结果，也没有实际 Flash ID 一项。诊断应查看 Status → Diagnostics 的 `Save Last`、`Flash Err`、`SPI2 Fault`、`SPI2 Reset`。

## R69 修改

在电机控制启动前，最多进行 **3 次识别尝试**。失败后使用现有 ENC2／Flash 仲裁器服务完成必要的 SPI2 Abort／复位恢复，每次间隔 2 ms，最多等待两次；已有单次 SPI 超时仍有效。成功后按原流程读取 A/B 保存副本，连续三次失败仍显示 `Save NO FLASH`，不自动写入默认配置，不假报成功。

未更改 SPI2 的 Mode 0／Flash /8、ENC2 的 Mode 1／/256、APB 时钟、片选配置、编码器五次停止／必要时重连策略，也未更改电机启动或保护。恢复期间可能按原服务逻辑执行 SPI2 外设复位，但不修改其配置参数。

每次 ID 尝试先清除底层旧错误，避免误把旧传输错误当成本次原因。初始化失败记录到原 `Flash Err`：操作 8／9 为命令／数据传输失败，11 为未取得总线；新增 **`12/0/00/00`** 表示 HAL 传输没有报错，但 ID 不被现有厂家判据接受，不包含实际 ID 字节。若重试成功，最近一次初始化失败仍保留，之后开始设置保存或成功保存会沿用原逻辑清除。

本次只补启动阶段的有限恢复，没有后台反复重新加载设置，以免覆盖用户当前 RAM 编辑；若三次全部失败，仍需结合诊断排查并重启。该补强尚未实板复测，不能宣称此次间歇故障已完全解决。

## 验证

真实 `MT6701.c + w25q64.c + app_storage.c` 配 SPI/NOR 模型：注入前 1／2 次 JEDEC 命令超时、前 1／2 次返回无效 ID，验证有限重试恢复；连续 3 次失败保持 NO FLASH、拒绝保存并保留错误；恢复后重新加载原有效副本，重试期间不擦写设置扇区。旧代码在首个瞬时失败场景即失败，新代码通过。

电机／编码器／HSO／协议、UI／存储／LCD 回归通过；Debug／Release 构建、启动强回调和 ELF/BIN 一致性检查通过，SPI2 初始化在链接后仍包含 GPIO／DMA／中断设置。初始化源文件及编码器仲裁器保持原值。
