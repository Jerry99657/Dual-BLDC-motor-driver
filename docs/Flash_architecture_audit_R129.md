# R129：从业务重复与状态维护审查 Flash 优化方向

审查日期：2026-11-08。对象为当前 R129 源码与已有 Debug／Release ELF、MAP、BIN。本轮只审查，没有修改固件源码、官方库、CubeMX 配置或编译参数，也没有重编译、烧录。

当前两种构建的 BIN 均为 130616 B，Flash 剩余 456 B。以下函数尺寸来自 Debug 链接符号；LTO 的内联与常量合并会改变归属，函数大小不是可回收大小，也不能简单相加当成某个源码文件的成本。

## 结论与顺序

仍存在可进一步收敛的业务重复，下一轮应优先减少同一动作经过的适配、同步和发布次数。不能把所有重复检查当作冗余，也不能从源码行数推断净节省。

| 顺序 | 方向 | 证据强度 | 建议 |
| --- | --- | --- | --- |
| 1 | 设置 A/B 记录加载与选择 | 两份源码路径、两组实际链接调用 | 先共用选取与发布逻辑，再处理启动重复读取 |
| 2 | 同一事务内重复发布 | 实际链接调用／明确调用链 | 删除多余配置重建，明确一次确认目标发布 |
| 3 | 工作模式／驱动／型号的 UI 与串口入口 | 两套适配分支仍存在 | 共用应用业务入口，前端只解析及展示结果 |
| 4 | 参数解码、默认值与 UI 视图同步 | 多处维护相同规则 | 统一确认值和规则的来源，保留独立编辑草稿 |
| 5 | 复杂诊断文字的按字段格式化 | 现有组格式化仍有无关分支工作 | 在已有描述表基础上做局部试点 |
| 6 | 编码器纯发布／有感对齐生命周期 | 部分重复，硬件及时序差异大 | 暂缓，不能为了共享而合并 SPI1／SPI2 策略 |

本轮未实施 A/B 变更，未给出每项可节省多少 B／KiB 的估算。优先级兼顾了可验证性和实现风险，不只按函数尺寸排序。

## 1. 设置记录被读取和选择两次

位置：`mycode/app_storage.c:204` 的 `AppStorage_Init()`、`:275` 的 `AppStorage_Load()`；调用来自 `Core/Src/main.c:222` 和 `mycode/ui_app.c:1669`。

初始化和重新加载各自读取 A/B 两份记录，比较序号，选择有效记录并更新 RAM 设置与活动地址。正常 LCD 启动路径先调用 Init，随后 UI 复位又调用 Load。

反汇编也确认 `settings_read()` 有四个调用点：

| 所属链接函数 | 调用地址 |
| --- | --- |
| `AppStorage_Init.isra.0` | `0x0800BAD4`、`0x0800BAE0` |
| `main`，包含内联后的 UI 初始化 | `0x08019FF0`、`0x08019FFC` |

`settings_read()` 的版本迁移／CRC 校验本来已经共用，不应再重复抽取它。应收敛的是两套 A/B 选取及 RAM 发布过程。

建议先抽出一份加载／选择实现，保留两个入口各自的失败策略：Init 两份无效时恢复默认，现有 Load 两份无效时没有同样的覆盖分支，不能机械合并为一种失败行为。然后明确启动时设置只加载一次，UI 使用已加载结果；显式重新加载接口保留。保留全部旧版本迁移、序号回绕比较、A/B 掉电恢复及日志扫描。

这项同时有机会缩短启动 I/O；单纯少读两次不会自动减少 Flash，必须连同重复的选取与调用路径一起测量。

## 2. 同一事务内发生重复发布

### M2 型号选择重复重建配置

`mycode/motor_control.c:368` 的 `MotorControl_SelectProfile()` 在 M2 分支执行：

```c
reset_m2(); save_config();
/* 随后的共同成功分支 */
clear_saved_axis(axis); save_config();
```

实际 ELF 中该函数也有两处 `save_config()` 调用：`0x080134B4`、`0x080134CC`。不是只在源码中看起来重复。

`save_config()` 当前为 124 B，但删除其中一次调用不等于回收 124 B，因为函数仍被其他入口使用。建议保留清理目标后的最终配置发布，核对前一次是否还存在必要副作用。回归应覆盖 Custom／预设互换、M1 状态、油门位、焦点和掉电保存。

### 本地参数提交两次写入目标

`mycode/ui_app.c:1539` 的 `ui_store_current()` 先调用 `AppSettings_StoreAxis()`，后调用 `AppSettings_StoreTargets()`。

前者在 `mycode/app_settings.c:51` 校验／限幅并复制三个目标；后者在 `:69` 再复制原参数中的三个目标，并处理油门。这里需要明确“确认目标只发布一次”，将油门等附属字段与目标发布分清。

不能直接认定两次写入的值永远相同：前一次可能限幅，后一次复制的是传入值。需对降 Speed Limit、切轴、远程命令和保存读回做对照，避免后写覆盖规范化结果。

以上属于边界较清楚的小项，不应宣称能单独释放大量 Flash。

## 3. 数值设置已共享，配置动作仍分叉

已经实现的部分：`AppSettings_Apply()` 是本地与远程数值设置的共同业务入口，不能把现状描述成所有设置都写了两遍。

残留分支：`mycode/protocol.c:201` 的 `apply_configuration()` 和 `mycode/ui_app.c:1855` 附近的 `apply_event()`，各自适配 Work、Feedback／SixStep、Motor、Focus、Align 等操作。本地侧分别维护刷新、保存标记和提示，远程侧再经过 `App_ConfigChanged()` 等同步过程。

建议将这些动作也收敛到带轴号的应用请求入口：解析与菜单映射属于前端，实际动作、确认值发布和变更通知属于业务层。结果携带必要的变更范围，UI 再决定刷新／提示，通信再生成原协议回执。

实现应沿用小型枚举和固定参数，不引入动态命令对象、虚函数或大量函数指针表。保留旧文本命令与 App RPC、来源所有权、过期请求、显式停止和对齐的时序限制。

这是更有希望的结构性方向，但收益不能按两个 switch 的行数相加：底层 `MotorControl_*` 本来已经共用，主要收敛的是上层适配与同步尾部。

## 4. 确认参数与视图同步的规则分散

### 限幅与默认值的重复解释

`AppSettings_ReadAxis()` 对标志位中的 Speed Limit、Pos Speed 做解码、默认值处理及电机上限归一化；`motor_control.c:116` 的 `speed_limit()`、`:124` 的 `position_speed()` 也维护对应规则，UI 还有位置速度上限联动。

建议区分两层：配置发布时共用一份规范化规则，运行时读取已确认结果；输出提交仍独立检查当前安全状态。初步可先共享纯解码／规范化函数，不立即改变存储布局或引入更多缓存。

不能把调用点全部删除：编辑器的范围提示、持久化记录的兼容处理和运行中的保护限制职责不同。

### 更新另一轴仍需要临时切换 UI 视图

`ui_app.c` 的 `refresh_config_views()` 会保存当前视图，逐轴加载、同步、保存，再恢复焦点。`App_SelectMotor()` 在 UI 已初始化时也先临时加载另一轴，调用依赖 `s_view_axis` 的本地适配，再切回。

底层 `AppSettings_SelectMotor(axis, profile)` 已经支持明确轴号，说明这层临时视图切换不是控制业务的必需条件。建议轴号贯穿业务与缓存更新，避免为了修改另一轴而模拟切换界面。

Run 草稿与确认值的分离必须保留，不能把 `current_view`、两轴缓存和持久化记录都当成可删除的副本。尤其 `int_bindings` 持有稳定变量地址，直接把当前视图改成指针可能导致编辑器仍指向旧轴。应先收敛确认值同步，最后再评估草稿结构。

这一项也可能主要改善 RAM 和维护成本，未必能明显减少 Flash；需要实际链接验证。

## 5. 复杂诊断行仍有按组格式化的残留

当前 `refresh_info()` 链接大小为 3100 B，`refresh_values()` 为 348 B。普通数值行已经使用 3 B 的 `ValueRow` 描述表，并会按查询字段跳过无关行；这项优化已经完成，不能再提一遍当成新收益。

尚有机会的部分是复合文字／状态：`App_ReadRow()` 建立 `TextQuery` 后调用整组 `refresh_info()`，`text_destination()` 把非目标结果指向 scratch。部分 `UiText_Format()`、字符串选择及辅助计算仍会执行，再将无关结果丢弃。

建议保留已有紧凑描述，先挑一组复合行，实现明确字段入口，LCD 批量刷新和 GetRow 都调用同一实现。不能另写一套远程 formatter，也不要把“减少无关格式化调用”直接等同于“减少 Flash”。新增索引／描述数据可能抵消指令节省。

## 6. 双轴相同算法之外仍有发布与生命周期重复

`MT6701.c` 的 SPI1 完成回调与 `second_publish()` 都执行解码后的零帧判定、角度换算、状态、采样时间／序号及有效样本发布。CRC、帧解码、零码观察和时间发布本身已经共享；只能继续评估剩余公共发布段。

不建议将整个驱动强行改为一个“通用编码器状态机”：ENC2 有 SPI2／W25Q 仲裁、未启用五次停止、实时模式低频重试等不同策略。M1/M2 的有感对齐也存在 3 s 生命周期的相似部分，但 M1 暂停快速环、M2 预留 SPI2 等行为不同。

该方向放到后续，先只评估纯数据发布／纯状态转换，保留 DMA 所有权、缓冲发布顺序、超时、故障计数及恢复策略。当前工程已共享测速器、电流环和调制器，不能把这些已完成的共用再计为新空间。

## 排除的误判

1. `AppStorage_Save()`、`settings_write()`、`W25Q_PageProgram()`、阻塞式 `JerryFOC_alignSensor()` 没有进入当前 ELF。源码可以另作清理，但直接删除不会释放当前 Flash。
2. JustFloat 与 Native 曲线已经共用 `telemetry_curves()`，并不是两套完整曲线业务。Native 额外状态／诊断帧属于现有功能。
3. 版本 1～6 设置迁移仍被启动读取使用，不能作为“旧版本垃圾代码”删除。
4. 同名函数的重用、相同字符串常量的合并和未引用函数裁剪已有编译器／链接器处理，不能把重复文本直接当成重复占用。
5. 命令接收与执行、外环与 PWM 输出门控之间的再次校验，很多用于捕获中途发生的急停、采样失效或来源变化。不能以“统一入口”为由取消这些校验点。

## 实施建议与验收

第一轮处理 1、2 项的确定重复；第二轮处理 3、4 项的业务入口与确认值同步；第三轮仅对 5 项做一个组的试点。6 项暂缓。

每项单独记录基线，保持同一工具链及编译选项，构建 Debug／Release 并计入表、字符串、初始化代码、RAM 与栈成本；只根据实际净差保留体积优化。运行对应的存储、UI、协议、来源／停止及控制保护回归，不把模块拆分或代码行数减少作为验收。

链接证据位于忽略的 `build/architecture-audit-r129/linked-evidence.json`，包含当前 BIN 哈希、函数尺寸、两组设置读取调用和两次配置发布调用。尚未进行这些候选变更的 A/B 构建，因此没有已实现的新空间收益。
