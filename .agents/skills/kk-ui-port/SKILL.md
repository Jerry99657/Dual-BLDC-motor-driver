# KK_UI 移植

以目标工程的实际 KK_OLED 公共接口、刷新语义、逻辑屏幕尺寸和构建系统为事实来源。KK_UI 是可编辑的项目副本，不是不可修改的外部二进制。

## 工作流程

1. 修改前检查版本控制状态，并发现已有 `KK_UI`、`KK_OLED`、构建文件、输入入口、毫秒时基和显示刷新调用。保留所有本地修改。
2. 若已有 KK_UI，逐文件检查其版本、接口和项目改动，只做任务所需的增量修改；不得用 Skill 资产静默覆盖、回退或合并已有副本。
3. 若尚无 KK_UI，从 [assets/kk-ui-runtime](assets/kk-ui-runtime/) 复制一份可编辑源码和 MIT 许可证到项目合适位置；可调用 `scripts/install_runtime.py <目标目录>` 完成仅首次安装。安装器遇到已存在目标会拒绝且不写入。不要直接从 Skill 目录参与构建。
4. 完整阅读 [porting-strategy.md](references/porting-strategy.md)，确认目标是 1 bit 单色图形画布、旋转后的逻辑宽高、字体/图标资源和输入方式。当前资产只验证了 128×64，其他尺寸必须在项目副本中调整并验证。
5. 根据目标工程已有实现和当前接入方案，确定 KK_OLED 所选 blocking、IT 或 DMA 刷新及 Busy 期间的缓冲契约。不能从函数名猜测双缓冲语义；当前无法执行的验证留待后续，不阻塞其他接入工作，也不能被误报为已经通过。
6. 接入源码、头文件路径和编译期配置。OLED 仍由应用初始化；随后初始化 KK_UI。把唯一的完整场景刷新所有权交给 KK_UI，移除应用层并行清屏或提交。
7. 在项目层把 GPIO 或编码器归一化为 `KK_UI_Input`。中断只累计原始输入状态；所有 KK_UI API 从同一个主循环或线程调用。
8. 首次接入需要建立初始应用，且用户未指定具体产品界面时，即使只要求“移植”，也衔接 `kk-ui-use` 安装其完整标准 Demo：应用、字模和图标一同复制到项目源码目录，保持图标首页和主要功能覆盖，不能只交付一个最小列表菜单。检查目标 KK_OLED 对比度能力并接入或明确禁用亮度演示。已有产品界面保留原界面；有具体需求时按需求使用 `kk-ui-use`。
9. 沿用目标工程自己的构建、测试和运行方式执行 [verification-checklist.md](references/verification-checklist.md) 中适用的检查。说明已完成结果和待验证项目，不规定固定工具，也不因某项暂不可执行而停止其他移植工作。

## 默认应用与需求澄清

移植所需的硬件与工程事实和产品 UI 功能需求分开处理。屏幕尺寸、KK_OLED 刷新语义、输入来源或构建接线等事实缺失，且会影响接入时及时确认；产品菜单尚未确定不阻塞标准 Demo 接入。

标准 Demo 是已确定的演示方案，不需要用户重新设计菜单。按 `kk-ui-use` 的 [standard-demo.md](../kk-ui-use/references/standard-demo.md) 接入并验证；不因缺少产品需求而停在最小样例，也不临时设计另一套演示界面。硬件、输入、刷新和构建按目标工程适配，128×64 下字体、图标、行高和动画保持参考基准。其他逻辑尺寸依照移植策略调整并报告差异。

用户明确要求产品界面时，再讨论真正缺失的入口、菜单层级、数据与操作、返回和反馈需求。Demo 不代表用户的产品需求。报告实际完成的验证与待验证项目，不用构建成功代替交互或实屏验收。

移植 KK_UI 不以 KK_OLED 先绘制检测画面或完成某种固定验收为前置条件。遵循目标工程自己的开发与验证习惯，不引入或要求特定的调试、下载、测量工具；某项条件暂不具备时，将其列为待验证并继续其他可执行工作。只有控制器、逻辑尺寸或实际刷新语义等关键信息确实无法确定时，才暂停受其影响的部分，不阻塞其他移植内容。

## 不变约束

- 不引入动态内存、通用控件树、运行时菜单注册或额外帧缓冲。
- 页面描述、文字、图标、字体和变量指针在 UI 生命周期内持续有效。
- 目标 KK_OLED 不允许 Busy 期间安全绘制时，改调度为“Busy 期间只更新逻辑状态，空闲后重画并提交”，不能修改正在发送的缓冲。
- 对已有工程副本先比较后修改；若资产与项目实现冲突，以用户工程和已确认需求为准。
- 换 MCU、SDK、I2C/SPI 或 OLED 控制器本身属于 `kk-oled-port` 的范围，不能在 KK_UI 中复制一套硬件驱动。
