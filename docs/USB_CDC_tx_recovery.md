# USB CDC 发送停止排查与修复（UI-R20-USB）

现象：运行一段时间后电脑不再收到遥测，但仍能发送命令，板子也执行命令；复位才能恢复。

本次静态检查发现两处确定的代码问题，能够解释这种单向停止。尚未在实物上抓到故障时刻，因此不能断言它们是所有类似故障的唯一原因。

## 原因

原 `Telemetry_Service()` 先调用 `CDC_Transmit_FS()`，返回成功后才设置应用层 `usb_tx_busy=1`。USB 发送完成中断可以在函数返回前发生，先将该标志清零，主循环随后又置为 1。之后所有遥测都被应用层拦住。USB 类驱动实际上已空闲，接收和命令执行仍正常，但应用层没有机会恢复。

原 USB 双缓冲在 TIM2 每次产生遥测时无条件轮换写入。电脑接收变慢时，仍在发送的缓冲区也会被覆盖。当前一帧为 104 字节，超过 FS 单个 64 字节数据包，覆盖还可能破坏同一帧后续数据包。另外，主循环在提交后清除 ready 标志，会丢掉提交期间由 TIM2 发布的新帧。

## 修改

- 删除应用层重复的 busy 标志，直接通过 `CDC_TxReady_FS()` 检查 CDC 类驱动的 `TxState`。
- 保留两个 128 字节缓冲区，分别作为最新待发送帧和正在发送帧。待发送数据允许被新遥测替换，正在发送的数据直到驱动空闲都保持不变。
- 主循环用一个短临界区复制待发送帧并清除邮箱，然后提交发送。提交之后不再修改邮箱状态，避免覆盖中断发布的新帧。
- 发送接口在短临界区内检查枚举状态、接口就绪状态和类指针，再提交数据，防止复位/反初始化期间访问已释放的类数据。
- 挂起或未枚举时暂停发送，恢复配置且驱动空闲后继续。发送提交被拒绝时舍弃该遥测帧，由下一次 10 ms 遥测更新补充。USB 接收命令和串口遥测格式保持原样。

没有加入“超时直接清 TxState”或周期性 MCU 复位。电脑未读取数据时，合法的 IN 传输也可能长期处于忙状态，此时缓冲区必须保留。当前修改解决重复 busy 标志造成的永久拦截；若 USB 硬件或类驱动本身始终不完成传输，需要继续检查端点/主机状态，不能仅清标志并覆盖缓冲区。

## 验证

- `python tests/motor_host/run.py`：发送完成抢先返回、新帧在提交期间发布、连续 1000 次提前完成、忙期间 1000 次更新且活动数据不变、最新帧保留、BUSY/FAIL 后继续、断连重连及原有电机/HSO/协议回归通过。
- `python tests/usb_host/run.py`：编译真实 `usbd_cdc_if.c` 和 ST USB 头文件，模拟底层 CDC 类；检查未配置/空指针/挂起、busy、收发并行、完成回调、重连以及中断屏蔽状态恢复通过。
- `python tests/ui_host/run.py`：界面、存储、显示驱动回归通过。
- Debug：Flash 113940 B，RAM 21344 B；Release：Flash 112604 B，RAM 21048 B。均编译成功，保留原有 RWX LOAD segment 链接警告。

以上为主机模拟与交叉编译结果，没有代替实机 USB 长时间运行验证。

## 板上复测

烧录 `build/Debug/FOC_two.elf` 或 `build/Release/FOC_two.elf`，在 About 确认 `FW = UI-R20-USB`。按原先会发生问题的方式持续采集遥测并发送指令；在安全的电机运行条件下，另外验证关闭并重新打开电脑串口、暂停后恢复采集以及 USB 拔插后重新打开串口。

若仍出现“能发命令但收不到数据”，调试器优先观察：

| 变量 | 用途 |
| --- | --- |
| `hUsbDeviceFS.dev_state` | 是否为 `USBD_STATE_CONFIGURED` |
| `g_usb_cdc_ready` | CDC Init/DeInit 生命周期状态 |
| `((USBD_CDC_HandleTypeDef *)hUsbDeviceFS.pClassData)->TxState` | 类驱动是否仍在等待发送完成；先确认指针非空 |
| `usb_tx_pending_len` | TIM2 是否还在生成遥测 |
| `hpcd_USB_FS.IN_ep[1]` | 驱动 IN 端点传输进度 |

如果 TxState 已为 0 且邮箱一直有数据，应检查主循环是否持续执行；如果 TxState 一直为 1，应记录端点状态并检查主机是否持续提交读取请求。
