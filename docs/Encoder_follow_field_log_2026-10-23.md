# 2026-10-23：Follow 编码器失联与磁铁对准实测记录

记录来源：用户实板观察，非自动采集。当前工程基线为 **UI-R43-ZEROLOG**，沿用其 `Zero/ZPre/ZPost/ZTime` 诊断格式；本次未再次记录板端 About → FW。M2 为手转主机、M1 为通电跟随的从机。

本次仅记录结果，按用户要求暂不继续修改代码、阈值、控制参数、通信时钟或恢复策略。保留当前基线，等待再次复现后讨论处理。

## 用户报告的故障数据

### 事件 A：开启 Follow 后报告 E2 LOST

| 项目 | 用户读数 |
| --- | --- |
| 跟随 Error | 3.32 rad |
| E2 Zero | NEAR 5 |
| E2 ZPre | 16383 |
| E2 ZPost | 155 |
| E2 ZTime | 250 ms |

前一个有效原始角度在绝对零点附近。`ZTime=250 ms` 与当前 ENC2 连续失败五次后、停机释放总线再低频重试的 **250 ms** 间隔一致，可能主要反映软件等待重试的时间，不能据此判断物理通信连续异常了 250 ms。原始码从 16383 经零点到 155，与跨零方向的变化相容，但中间包含重试等待，不能按相邻 100 μs 样本计算速度或认定零帧真实有效。

`Error=3.32 rad` 是跟随位置误差，不能当作编码器原始角度突然跳变了 3.32 rad 的证据。它与失联、停机的先后时序没有自动记录。

### 事件 B：报告 E1 LOST，但提供的行名仍为 E2

| 项目 | 用户原始标注及读数 |
| --- | --- |
| 故障标题 | E1 LOST |
| E2 Zero | NEAR 3 |
| E2 ZPre | 1 |
| E2 ZPost | 16383 |
| E2 ZTime | 0 ms |

**轴号待核对，保留原始标注，不擅自改写为 E1 数据。** 如果读取的确实是 E2，这组数据只能描述 E2 的最近全零事件，不能用于解释 E1 为什么失联。它与 E2 在零点附近短时往返的变化相容；0 ms 仅表示开始和恢复发生在同一个毫秒 tick 内。

`Zero` 记录的是最近一次全零事件，不独立锁存最初导致停机的事件。因此，`NEAR 3` 也不能直接等同于“本次 E1 失联只发生三帧全零”。事件可能来自另一轴或不是最初停机事件。

## 当前判断及限制

- M2 磁铁原先未对准，调整后 Follow 中 E2 LOST 明显改善：支持**机械安装是可能参与因素**，但尚未通过重复、同条件的前后对照确认因果。不能把现象定为纯偶然，也不能宣布根因已经解决。
- 两路记录都出现在原始零点附近，**合法全零帧被现有规则拒绝的歧义仍需保留**。磁铁对准后的改善本身不能排除该软件路径；目前不清楚调整是否同时改变了间隙、线束位置或经过原始零码时的运动条件。
- Single M2 通电运行约 20 min 基本正常，说明“只要电机通电/PWM 存在就一定会失联”不符合本次观察；仍不能排除双机时不同的供电/地耦合、共享总线或执行时序条件。
- Single M1、Single M2 的测试速度不同，Follow 又包含手转、往复和不同的零点停留时间，不能直接把这些测试视为等条件的硬件或软件排除试验。20 min 未观察到故障，也不等于低概率故障已被排除。
- E1 的偶发失联尚无一组已确认轴号的对应诊断，暂不归因于 M2 磁铁，也不据此放宽判帧、CRC、样本年龄或电流保护。
